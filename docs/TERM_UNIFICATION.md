# TERM_UNIFICATION — ko.json 용어 통일 가이드

> **이 문서는 AI(사람 포함)에게 주는 작업 지시서이자, 용어 대응표의 원장(living document)이다.**
> 사용자가 "용어 통일해줘"라고 시키면 AI는 **이 문서를 먼저 읽고** 아래 절차대로 작업한다.

---

## 0. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 배경 | 저장소(main)의 `frontend/src/locales/ko.json` 용어와, 사용자가 **실제로 운영·검증에 쓰는** `ko.json` 용어가 다르다. 주석·문서에 main 용어가 남아 있으면 다른 AI가 "이건 화면에 뜨는 말과 다른 말인데?" 하고 헷갈린다. |
| 기준(정답) | **사용자의 실제 `ko.json`**. main의 `ko.json`은 참고용이며 정답이 아니다. |
| 목적 | 코드 주석·docstring·문서(`*.md`)에 쓰인 용어를 **사용자의 실제 `ko.json` 용어**로 통일한다. |
| 통일 대상 | 제약 없음 — 저장소의 모든 텍스트 파일(§3). 단, **동작을 바꾸는 것은 건드리지 않는다**(§4). |
| 이 문서의 위치 | `docs/TERM_UNIFICATION.md`. CLAUDE.md 에는 등록하지 않는다 — **사용자가 통일을 지시할 때만** 참조한다. |
| 현재 대응표 상태 | §6 참조 (`마지막 동기화` 날짜 확인) |

## 1. 핵심 원칙

1. **사용자의 실제 `ko.json` 이 정답이다.** main 의 `ko.json` 과 값이 다르면 사용자 쪽이 맞다.
2. **바꾸는 것은 "설명하는 글"뿐이다.** 주석·docstring·문서 속 용어만 통일한다. 코드 동작·키·식별자는 그대로 둔다(§4).
3. **추측하지 않는다.** 대응이 확실하지 않으면 치환하지 말고 §8 의 보고 형식으로 묻는다(CLAUDE.md **규칙 K**).
4. **작업 전 계획 승인, 작업 후 검증**은 CLAUDE.md **규칙 A / C** 를 그대로 따른다.
5. **대응표는 계속 갱신한다.** 용어가 바뀌면 코드보다 먼저 §6 을 고치고, §10 변경 이력에 남긴다.

## 2. 입력물 — AI 가 받아야 하는 것

작업을 시작하기 전에 아래 두 가지가 모두 있어야 한다. 하나라도 없으면 **작업을 시작하지 말고 사용자에게 요청**한다.

| 입력 | 설명 |
|---|---|
| **A. 사용자의 실제 `ko.json`** | 사용자가 채팅에 붙여 넣거나 파일 경로로 준다. **이것이 기준.** |
| **B. main 의 `ko.json`** | 저장소의 `frontend/src/locales/ko.json` (`git show origin/main:frontend/src/locales/ko.json`). 현재 주석·문서에 남아 있는 "옛 용어"의 출처. |

> 사용자의 `ko.json` 이 저장소 파일과 **이미 같아졌다면**(사용자가 반영한 경우) B 는 `git log -p -- frontend/src/locales/ko.json` 의 이전 버전으로 대신한다.
> 어느 쪽이든 **"옛 용어 → 새 용어" 쌍을 만들 수 있어야** 한다.

## 3. 통일 대상 (제약 없음)

저장소에 있는 **모든 텍스트 파일** 안의 "사람이 읽는 글"이 대상이다.

| 종류 | 예시 |
|---|---|
| 코드 주석 | `frontend/src/**/*.ts(x)` 의 `//`, `/* */`, JSX 주석 / `backend/**/*.py` 의 `#` |
| docstring | Python 함수·클래스 docstring |
| 문서 | `docs/**/*.md`, `docs/**/*.html`(목업), `scripts/approval_cases/README.md`, 루트 `*.md` |
| 가이드 파일 | `CLAUDE.md` (용어 정리 절 포함) |
| 테스트·스크립트의 설명문 | 테스트 이름 문자열의 설명, 러너 케이스 설명 등 |
| 설정 파일의 주석 | `docker-compose*.yml`, `nginx/*.conf`, `.env.example` 의 주석 |

탐색 범위를 줄이지 않는다. 시작 시 아래로 대상 파일 목록을 뽑아 보고한다.

```bash
git ls-files -z | grep -zv -E '(^|/)(node_modules|migrations)/|\.(cer|png|jpg|ico)$' \
  | xargs -0 grep -Il '[가-힣]'
```

> `-z` / `-0` 는 `전체가이드.md` 같은 **한글 파일명**이 `git ls-files` 에서 이스케이프되어 grep 이 실패하는 것을 막는다.

## 4. 통일하지 않는 것 — 동작을 바꾸는 것

"제약 없음"은 **파일 범위**에 대한 말이다. 아래는 글처럼 보여도 **동작·데이터에 닿으므로 임의로 바꾸지 않는다.**
발견하면 **치환하지 말고 §8 형식으로 모아서 보고**한다(규칙 K).

| 건드리지 않음 | 이유 |
|---|---|
| i18n **키 이름** (`common.role_label_PL` 등) | 키가 바뀌면 `t()` 호출이 전부 깨진다. 통일 대상은 **값(용어)** 이지 키가 아니다. |
| 코드 **식별자** (변수·함수·클래스·컬럼·URL·API 필드명) | 동작 변경. 용어가 달라도 식별자는 영문 기준이다. |
| **런타임에 쓰이는 문자열** (DB 저장값, API 응답/요청 값, 비교·분기에 쓰는 리터럴, choices 값) | 데이터 호환성. 한글처럼 보여도 값 비교에 쓰이면 건드리지 않는다. |
| 사용자가 이미 준 `ko.json` 의 **값 자체** | 이게 기준이다. 되돌리거나 "수정"하지 않는다. |
| `en.json` 값 | 이번 작업은 **한국어 용어** 통일이다. 영문 용어까지 바꾸려면 사용자가 따로 지시한다. |
| 영문 **역할 약어** (`PL`, `SA`, `R`, `RV`, `P`, `PV`, `J`, `O`, `E`, `EV`, `RA`, `TE_*`) | 코드·권한과 직결된 고정 코드다. 약어를 한글로 바꾸지 않는다. (약어 옆에 붙은 **한글 설명**만 통일 대상.) |
| 마이그레이션 파일, 빌드 산출물, `node_modules` | 자동 생성·외부 코드. |

> 위 목록에 **없는데 동작에 영향을 줄 것 같은** 항목도 같은 방식으로 멈추고 묻는다.

## 5. 작업 절차

### 단계 0. 준비 (코드 수정 없음)
1. `CLAUDE.md` 를 다시 읽는다. (규칙 A)
2. 이 문서(§6 대응표, §7 모호 용어 결정 기록)를 읽는다.
3. §2 의 입력물 A, B 를 확보한다.

### 단계 1. 대응표 만들기 — "옛 용어 → 새 용어"
두 `ko.json` 을 **평탄화**해서 같은 키끼리 값을 비교한다.

```bash
# 예시: 평탄화 + 값이 다른 키만 출력 (작업 디렉터리는 프로젝트 밖에 둔다)
python3 - <<'EOF'
import json, sys
def flat(o, p=''):
    for k, v in o.items():
        if isinstance(v, dict): yield from flat(v, p + k + '.')
        else: yield p + k, v
old = dict(flat(json.load(open('OLD_main_ko.json'))))   # B: main
new = dict(flat(json.load(open('NEW_user_ko.json'))))   # A: 사용자 실사용
for k in sorted(old.keys() & new.keys()):
    if old[k] != new[k]: print(f'{k}\t{old[k]}\t→\t{new[k]}')
print('--- only in main :', sorted(old.keys() - new.keys()))
print('--- only in user :', sorted(new.keys() - old.keys()))
EOF
```

분류한다.

| 분류 | 의미 | 처리 |
|---|---|---|
| **값 변경** | 같은 키, 다른 값 | §6 에 `옛 용어 → 새 용어` 로 기록 (통일 대상) |
| **main 에만 있음** | 사용자는 키를 지웠다 | 주석에서 그 화면/문구를 언급하면 §8 보고 |
| **사용자에만 있음** | 새로 생긴 문구 | 주석에서 대응되는 옛 표현이 있으면 후보로 기록 |
| **값은 같고 키만 다름** | 키 이동/개명 | 용어 통일 대상 아님. 주석에 **키 이름이 적혀 있으면** 동작 확인 후 §8 보고 |

값 변경 중 **같은 옛 용어가 여러 키에서 서로 다른 새 용어로** 바뀐 경우(예: 옛 "요청서" → 어떤 곳은 "의뢰서", 어떤 곳은 "신청서")는 **모호 용어**다. 임의로 하나를 고르지 말고 §7 에 결정 기록이 있는지 본 뒤, 없으면 사용자에게 묻는다.

### 단계 2. 사용처 조사
옛 용어별로 저장소에서 쓰인 곳을 센다.

```bash
grep -rIn --exclude-dir=node_modules --exclude-dir=migrations -F '옛용어' . | wc -l
```

- 주석/문서/화면 문구 중 **어디에 쓰였는지**를 구분한다(§3 대상 vs §4 비대상).
- 화면에 직접 뜨는 문구(`t()` 로 렌더되는 값)는 `ko.json` 이 처리하므로 **본 작업 대상이 아니다.**

### 단계 3. 계획 제시 → 사용자 승인 (규칙 A)
CLAUDE.md 의 `📌 작업 계획` 형식으로 아래를 포함해 제시한다.
- 대응표(옛 → 새)와 용어별 사용처 개수
- 모호 용어 목록과 AI 의 제안
- §4 에 걸려 **건드리지 않을 항목** 목록
- 영향 파일 수와 목록

**승인 전에는 한 줄도 수정하지 않는다.**

### 단계 4. 치환
- 파일 단위로 작업하고 **파일별로 개별 커밋**한다(규칙 E).
- 일괄 `sed -i` 를 쓰더라도 **치환 전 `grep -n` 으로 각 매치를 눈으로 확인**한다(§5-1 주의사항).
- 한 커밋의 메시지 예: `docs(term): APPROVAL.md 용어 통일 (요청서→의뢰서)`

### 단계 5. 검증 (§9)
통과하지 못하면 보고하고, 임의로 넘어가지 않는다.

### 단계 6. 문서 갱신
작업이 끝나면 **이 문서의 §6(대응표), §7(결정 기록), §10(변경 이력)** 을 갱신한다.

### 5-1. 치환 시 주의사항

| 위험 | 대응 |
|---|---|
| **부분 문자열 오치환** — 옛 용어가 더 긴 단어의 일부일 때(예: "결재" ⊂ "결재선", "반려" ⊂ "반려됨") | 치환 전 `grep -n` 으로 문맥 확인. 긴 용어부터 치환(긴 것 → 짧은 것). |
| **조사 불일치** — "은/는, 이/가, 을/를, 으로/로" 는 받침에 따라 달라진다 | 용어를 바꾼 뒤 **바로 뒤 조사를 재확인**하고 필요하면 고친다. |
| **복합어·띄어쓰기** — "요청 서", "요청서류" 등 | 정확히 용어 단위로만 치환한다. |
| **같은 단어, 다른 뜻** — 옛 용어가 UI 용어가 아닌 일반 단어로 쓰인 경우 | 일반 단어는 바꾸지 않는다. 애매하면 §8 보고. |
| **영문 약어 보존** | `PL`, `TE_R` 등은 그대로 두고, 괄호 속 한글 풀이만 통일한다. (예: `PL(제품 담당자)` 의 풀이 부분) |
| **코드 블록·표·인용문 속 용어** | 마크다운 코드 블록 안의 **실제 코드·명령어·로그 원문**은 바꾸지 않는다. 설명 텍스트만 바꾼다. |
| **과거 이력 문서** (`FIX_PROGRESS.md`, `E2E_TEST_AND_BUGS.md` 의 날짜별 기록, 커밋 이력 인용 등) | 통일 대상이긴 하지만, **실행 출력 원문 인용**은 건드리지 않는다. |
| **모호 용어** | 사용자 결정 전에는 건드리지 않는다. |

> 기준은 **사용자의 실제 `ko.json`** 이다.

**동기화 담당 AI 세션:** `-`

## 9. 검증 (작업 후 반드시)

모든 항목을 **실제로 실행해** 결과를 보고한다. 확인하지 못한 것은 "확인하지 못했다"라고 쓴다(CLAUDE.md 규칙 C-1-3).

| # | 검증 | 방법 | 합격 기준 |
|---|---|---|---|
| 1 | 옛 용어 잔존 확인 | 단계 2 의 `grep` 을 다시 실행 | **통일 대상 범위**에서 0건. 남은 것은 모두 §6-4 / §8 에 기록된 것이어야 한다. |
| 2 | 동작 코드 무변경 | `git diff` 에서 **주석·docstring 이 아닌 줄**이 바뀌었는지 확인. 예: `git diff -U0 -- '*.py' '*.ts' '*.tsx' \| grep -E '^[+-]' \| grep -vE '^(\+\+\+\|---)' \| grep -vE '^[+-]\s*(//\|#\|/?\*)'` | 비주석 변경 0줄. (주석 확인용 간이 명령 — 결과를 눈으로도 확인) |
| 3 | `ko.json`/`en.json` 무변경 | `git diff --stat -- frontend/src/locales` | 변경 없음 |

## 11. 지속 갱신 규칙 (이 문서를 최신으로 유지하는 법)

1. **용어는 `ko.json` 이 먼저, 주석·문서는 그 다음.** 사용자가 `ko.json` 용어를 바꾸면 → §6 대응표를 먼저 갱신 → 그 다음 주석·문서를 통일한다.
2. **새 기능을 작업할 때도** 주석·문서에 쓰는 용어는 §6 의 **새 용어(사용자 실사용)** 를 쓴다. 옛 용어를 새로 들여오지 않는다.
3. **§6 의 `마지막 동기화` 는 항상 사실대로** 적는다. 사용자의 `ko.json` 이 바뀌었을 가능성이 있으면(사용자가 "용어 바꿨어"라고 했거나 날짜가 오래됨) 작업 전에 **재동기화(§5 단계 1)** 를 먼저 제안한다.
4. **통일을 지시받으면 이 문서를 반드시 먼저 읽는다.** (CLAUDE.md 에는 등록하지 않았으므로, 지시가 곧 트리거다.)
5. **결정은 §7 에 남긴다.** 같은 질문을 사용자에게 두 번 하지 않는다.
6. **이 문서의 규칙을 바꿀 때**는 §10 에 사유를 적는다.
